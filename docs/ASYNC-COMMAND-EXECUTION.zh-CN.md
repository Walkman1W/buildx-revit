# 异步命令与执行等待

## 当前链路与现场事实

点击命令后，HTTP 接口返回 `202 + executionId`，后台持有该次请求，最终状态通过 SSE 回传。浏览器的 12 秒期限是接单回执期限，不是整个 Revit 操作期限。原生 status 请求默认 60 秒、其他请求默认 150 秒；手动诊断可传独立观察期限，不能把诊断期限当成生产默认。

2026-11-02 的两个保留回执说明主要等待发生在 Revit 进入回调之前：

| 操作 | 队列创建至回执 | 已记录的业务执行 | 结果 |
|---|---:|---:|---|
| search_elements | 32.526 秒 | 1.001 秒 | 成功 |
| status（手动诊断期限 12 秒） | 13.813 秒 | 未开始 | 到期后拒绝执行 |

这两条是实际本机回执，不是等价的优化前后样本。不能据此声称查询计算慢、AI 推理慢，或断言全部延迟由队列排序造成。原生回调需要 Revit 的安全执行时机；HTTP 异步不会令 Revit 模型 API 可以在线程池调用。

## 已实施的边界

### 异步进度

页面按已有传输事件显示：准备本次请求 → 等待 Revit 返回 → 核对结果 → 终态。`waiting_revit` 表示原请求已发布、仍等回执；它不证明模型操作尚未开始，也不证明已经开始。只有原回执决定成功、失败、未执行或未知。

进度属于原会话、账号绑定、executionId 与 requestId。取消、身份变化、后续执行或终态之后的迟到事件不能恢复旧任务。相同阶段不反复广播；不为显示进度新增 Revit 状态查询。计时不包含参数、源码或模型结果。

### 队列公平性（宿主源码候选）

原宿主按随机 GUID 字典序挑选请求，而且观察与实际领取时各选一次；新来的低 GUID 请求可以抢过已观察的请求。候选按完成写入文件的时间排序、路径序仅作同时间决胜，并优先处理已接受的确切请求。原请求已消失、已被领取或已有回执时，重新选择并保持调度关联未知，不能假造匹配。

保持一次回调一个请求、Revit API 和事务在主线程、原有 pending 与错误退避规则。成功后的固定 500 ms 间隔暂留：没有真实 Revit 证据证明移除后不会造成漏醒或重入。本次没有把它或文件轮询冒充十几秒等待的唯一原因。

## 部署与验证范围

- Node/页面进度与行内“系统 / 个人”标签可独立加载；页面仍为统一命令列表。
- 队列排序和领取策略属于 Revit 宿主 DLL。当前 Revit 进程保持打开，未安装或热替换候选；仅重启 Node 服务不能改变已加载宿主。
- 受控 HTTP/SSE 与队列测试验证异步接单、进度归属、未知结果与不重试；原 C# 生产方法的隔离 fixture 验证公平排序和领取。它们不等同于真实 Revit 等待改善。
- 实际优化前后完整任务耗时、整个进程族 CPU/峰值内存和全部代理上下文 token 尚未测量。原生命令无需模型推理，但不能由此推导整个研发任务的 token 成本。

本轮加载后台更新后的单次真实只读验证：HTTP 接单 17.38 ms，首次等待状态 62.72 ms，最终完成 225.53 ms；1 个原生请求、0 推理 token。验证客户端 Node CPU 为 user 172 ms / system 78 ms，峰值 RSS 78,316 KiB；这些是客户端自身数据，不是 Revit 或服务进程族。记录位于 `artifacts/async-live-2026-11-02T03-26-02-463Z-b734d6a1/verification.json`。当前宿主仍为 0.6.5，因此这只是异步链路真实工作的一次样本，不能作为宿主队列修正的前后提速对比，也不能证明间歇性长尾消失。

## 继续缩短实际等待的顺序

1. 在下一次获准加载新宿主后，按同一命令、同一模型和空闲/操作中两种状态对比冷暖完整任务；不自动重放未知操作。
2. 固定原生写工具目前单独排一次文档状态核对，再排写入。可设计宿主在同一次回调核对完整来源身份、权限和执行，减少一次真实排队；不能通过缓存或省略校验实现。
3. 个人 C# 命令目前在 Revit 回调内每次启动编译器并等待。后续应将纯源码编译准备移到后台，对源码、签名、编译器与引用程序集身份建立有界缓存；模型读取、API 调用与事务仍留在 Revit 主线程。首轮冷编译和二次复用必须分开测量。
